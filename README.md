# StackChan 接入 Claude.ai

适用对象：官方 M5Stack StackChan，具备基础服务器与固件开发能力的个人开发者。

> 这是一份可对外分享的技术路线与实施教程，不是现成固件安装包。文中的域名、路径、设备信息都使用示例或占位符。功能名称是建议接口，不保证原厂固件已经提供；需要实现相应的桥接服务器与设备固件。

## 一、先明确要实现什么

目标是在保留原厂小智的前提下，让 Claude.ai 通过远程 MCP 控制机器人：说话、显示字幕和表情、转头、拍照、播放上传音频，以及读取触摸和摇晃记录。

推荐把原厂模式与外接模式做成两个独立入口：

- 小智模式：原厂语音对话正常运行。
- 远程 AI 模式：允许外部 MCP 命令，暂停原厂回复对同一麦克风、扬声器和动作的竞争。
- 触摸记录等被动采集可以独立运行，不要求 AI 客户端保持打开。

重要边界：连接器能让 Claude 调工具，不代表机器人一有新消息就能自动唤起 Claude.ai。手机里发起聊天后远程控制，和完全无人值守的自主语音聊天，是两条不同的实现路线。

## 二、整体架构

```text
用户在 Claude.ai 发起请求
        ↓
Claude 远程 MCP 客户端
        ↓ HTTPS + OAuth
公网桥接服务器
        ↓ 经过认证的设备 WebSocket
StackChan 固件
        ├─ 动作与表情
        ├─ 字幕与音频播放
        └─ 抓拍 JPEG → HTTPS 上传 → MCP 返回图片
```

远程 MCP 连接由 Claude 云端访问服务器。服务器必须具有公网可达的 HTTPS 地址，不能只在局域网或开发者电脑上可访问。

语音回复另有一段媒体链路：

```text
AI 生成回复文字
    ↓
TTS 服务合成音频
    ↓
服务器转码为设备支持的格式
    ↓
设备下载完整文件
    ↓
解码播放，同时显示字幕和指定表情
```

## 三、需要准备的东西

1. 一台明确型号和硬件版本的 StackChan，可靠 USB 数据线与稳定供电。
2. 一台可以部署服务的服务器。配置需求取决于是否在本地运行模型或 TTS；只做桥接时不需要 GPU。
3. 域名与有效 HTTPS。可以使用反向代理或受控隧道，具体取决于部署环境。
4. Claude.ai 账号及支持远程自定义连接器的客户端/账号权限。入口和可用性可能随产品更新。
5. 与设备原固件相匹配的源码、ESP-IDF、依赖版本、烧录和串口工具。
6. 一个 TTS 方案。测试阶段可选择无需模型推理的现有语音服务，长期使用应确认授权、费用、隐私与稳定性。

不要先从“下载别人二进制刷进去”开始。不同主控、显示屏批次、分区表和驱动版本可能不兼容。

## 四、推荐的实施顺序

### 第 1 步：确认硬件与备份

记录主控型号、屏幕版本、原固件版本、Flash 大小和实际串口。

读取并保存完整 Flash 备份、分区表及 OTA 选择数据。用 SHA256 校验备份文件，不仅检查文件是否存在。

完整备份可能含 Wi-Fi、激活和设备认证信息，不能公开分享。

如设备有双 OTA 槽，可优先在测试槽运行修改版、保留原厂槽。必须先确认分区地址和大小，**不要照抄其他机器的烧录偏移**。

回滚方案应先准备好：如何选择原厂槽、如何恢复分区或固件、如何在应用无法启动时进入下载模式。自动 OTA 回滚不是无条件可靠的恢复手段。

### 第 2 步：核对源码与构建环境

确认源码版本确实对应目标设备和固件，固定 ESP-IDF 与组件版本。

先编译不带业务改动的基线，验证屏幕、触摸、相机、音频、舵机及原厂联网功能。

不要同时升级底层 SDK、替换 UI 和增加网络协议。一次改变太多，很难判断故障来源。

### 第 3 步：先做桥接心跳

服务器提供：

- 公网 HTTPS 入口。
- 设备 WebSocket 入口。
- 独立设备认证。
- 在线状态与最后心跳时间。

设备 hello 消息建议包含协议版本、设备标识、支持能力及当前控制模式。

先只验证连接、掉线检测和自动重连，不加入动作。设备凭据与 MCP 用户授权凭据应分开，不能互相借用。

### 第 4 步：搭建 MCP 与 OAuth

服务器提供受保护的 MCP 控制入口，例如：

```text
https://robot.example.com/control/mcp
```

如果另外提供公开健康检查，它只能报告基本状态，不能暴露控制、照片、留言或凭据。

需要实现的授权能力通常包括：OAuth 发现文档、适用的客户端注册方式、PKCE、权限范围、资源绑定、短期授权码和令牌刷新。优先使用维护中的 MCP/OAuth 库。

所有者授权页面应验证请求状态、防伪参数和来源，设置合理过期时间。不要把完整带令牌链接当作公开连接地址。

建议第一批 MCP 工具：

| 工具 | 用途 |
|---|---|
| get_control_status | 查询设备在线、控制权和能力 |
| set_head_yaw | 有界角度的低速转头 |
| set_expression | 切换受支持表情 |
| speak_text | 合成、播放语音并显示同一段字幕 |
| take_photo | 抓拍一次并返回图片 |
| get_camera_status | 查询上次拍照失败阶段 |
| get_music_status | 查询下载、解码及播放状态 |

每个命令带唯一 ID，返回 accepted、rejected、unavailable 或 unknown 等明确结果。

**accepted 仅代表软件接受；unknown 代表结果不确定，不等于没有执行。** 对拍照、说话和动作，不要在 unknown 后自动重复发送。

### 第 5 步：在 Claude.ai 添加连接器

在 Claude.ai 的自定义/连接器设置中添加远程自定义连接器，填写桥接服务器 MCP 地址。

选择与服务器匹配的认证方式。如果服务器只支持动态客户端注册，选择自动注册；不要误选服务器尚未支持的客户端身份方式。

完成授权后，先要求 Claude 仅调用状态查询，不要立即控制舵机或拍照。

成功标准是实际返回设备状态，而不是页面只显示“已连接”。工具列表可能被客户端缓存，新增工具后需要刷新连接器工具列表或重新进入聊天。

### 第 6 步：做独立的远程模式

在机器人导航里增加远程 AI 页面，物理进入该页才交出控制权。

服务器与设备均检查模式。只在服务器上设置一个布尔值不够，因为旧命令或不同客户端仍可能发来请求。

离开远程模式时，明确处理正在播放的音频、待执行动作、表情恢复和收音状态，再恢复原厂模式。

不要把本地摸头反馈与原厂 AI 云端控制混为一谈：前者可以保留，后者需要隔离。可以让远程命令短暂优先，本地互动在之后恢复。

原厂 UI 若是进入语音应用后销毁导航、退出时重启回导航，不宜直接假定能无缝切换；先沿用可验证的生命周期，再考虑改造。

### 第 7 步：逐项开放控制

推荐顺序：状态查询 → 小幅转头 → 基础表情 → 音频播放 → 带字幕说话 → 拍照 → 传感器历史。

动作需要设备侧限制角度、速度和时长，不能只依赖提示词。先小幅验证，再恢复原位。

两轴头部能左右转和抬低头，不代表能向肩膀方向侧倾。效果设计要匹配实际自由度。

### 第 8 步：打通声音、字幕与表情

先播放一个已知短音频，确认音频解码和扬声器输出。然后再接 TTS。

一种可行的测试配置是 Ogg/Opus、单声道、16 kHz、固定帧时长；这不是所有设备的通用要求，必须匹配目标固件解码器。

转码服务应限制输入协议、时长、输出大小和资源占用。不要把外部 URL 直接拼进 shell 命令。

说话最好使用一个原子命令，同时携带音轨、字幕和表情。单独先发 emote 再发 speak，可能在队列、网络或恢复逻辑中互相覆盖。

播放前暂停唤醒/收音并关闭竞争语音通道，避免把自己的声音识别为新留言。播放结束后恢复可唤醒待机，清除字幕并恢复原表情。

单纯 play_music 通常只播放音频，不会自动有字幕或说话表情。应有独立 speak_text 或同等接口。

### 第 9 步：单独验证相机链路

拍照不是一个单一动作，应拆成：

```text
取得相机对象 → 获取相机锁 → 抓帧 → JPEG编码 → HTTPS上传 → 服务器校验 → MCP返回图像
```

分别返回失败阶段、HTTP 状态和编码后图片大小。不要把所有失败写成“相机忙”。

上传必须绑定当前拍照命令 ID 和设备连接，校验 JPEG 类型、大小、起止标记，并拒绝过期请求与重放。不要把抓拍图放成无鉴权公开 URL。

相机操作较慢，不能让同一个任务阻塞心跳太久。可以使用独立工作任务，或实现有界的拍照保活和超时管理；不要简单无限延长掉线判断。

验证时只拍一次，再读诊断。不要因模型猜测“固件没连上”就反复重启或重刷。

### 第 10 步：做传感器事件与留言持久化

触摸/摇晃事件建议保存：唯一事件 ID、事件类型、设备运行毫秒、服务器接收时间。

服务器数据库提交成功后再 ACK。设备遇到断线可以重发同一事件 ID，服务器按唯一键去重，不能重复累计。

已上传的事件或文字留言保存在服务器，不应因机器人重启消失。设备 RAM 内尚未上传的数据是否需要本地持久化，是另一个独立需求。

原厂能识别哪些事件，必须核对固件实际启用逻辑。有 IMU 不等于已经实现拿起、放下、跌落等所有事件。

## 五、语音输入的两种路线

### 路线 A：留言式，不自动唤起模型

机器人识别语音 → 文字保存服务器 → 用户以后在 Claude 发消息 → Claude 读队列并生成回复 → 保存回复 → TTS 播放。

可以复用现有 ASR；但如果只是在本地丢弃原厂回答，不能宣传为原厂云完全没有生成回答。

队列读取不应删除留言；明确回复成功或处理完成后再更新状态。重复提交同一回复要幂等，未知播放结果不能自动重播。

### 路线 B：无人值守自主聊天

需要服务器上的模型调用入口或官方支持的持续运行客户端，收到新文字后能自主生成回复，再调用 TTS 与设备。

Claude.ai 远程 MCP 连接器本身不能代替这个后台推理入口。是否使用模型 API、订阅支持的官方方案或本地模型，需要另行确认服务条款、地区、费用、额度与可用性。

不要依靠复制网页登录令牌、逆向私有接口或浏览器自动化，把订阅聊天账号当作已获支持的通用推理 API。

## 六、踩过的坑与处理方法

### 1. “已连接”不等于机器人在线

OAuth 成功、MCP 服务器可达、设备 WebSocket 在线、当前页面允许控制，是四个不同状态。诊断工具应逐项报告。

### 2. 命令超时，但画面实际上已执行

网络延迟或 ACK 丢失可能导致 unknown，设备已经显示表情或执行动作。不能自动重发；先读状态或请现场观察。

### 3. 表情只有三秒，调用结束时已经看不到

视觉验收使用更长且有上限的展示时长，并给出设备端表情状态。软件状态与现场可见效果仍需分别确认。

### 4. 一次性关闭所有本地反应，机器人变得没有互动

隔离外接 AI 与原厂 AI，不等于必须禁用摸头、摇晃的本地反馈。应区分控制来源，并制定短暂优先规则。

### 5. 字幕和表情有了，声音却没有

它们可能在音频下载完成前已显示。先检查 HTTP 状态、实际下载字节数、入队帧数、输出帧数和解码错误。

HTTP 200 不代表文件完整。曾遇到只下载一小段即失败、解码与输出均为零。修复包括完整长度校验，以及仅在出声前做有限下载重试。不能重播已输出的内容。

### 6. TLS 上传时 AES 内存分配失败

抓拍与 JPEG 编码成功，并不代表还有足够的连续内部内存做 HTTPS 加密。实际遇到过：

```text
AES allocation failed
→ TLS write failed
→ SSL send failed
→ HTTP request send failed
```

一次把整段图片请求交给 TLS 加密，会提高瞬时内存需求。一种实测有效的改进是限制每次 TLS 写入大小，例如 1024 字节，按实际发送字节数推进偏移。保持原有证书验证、加密和发送顺序。

该改动会影响共用 TLS 库的其他功能，需要回归语音、WebSocket 和相机；不要当成所有内存问题的通用药方。

### 7. “JPEG有几千字节”被误解为服务器只收到几千字节

诊断字段必须命名明确。设备编码后的 JPEG 大小，与服务器接收量是两回事。

如果上传请求未成功打开、HTTP 状态为零，只能说明没有取得有效 HTTP 响应，不能凭编码大小判断“传到一半断了”。

### 8. 心跳按短时间窗口判断，忙时漏发

用时间除法比较跨界、仅在每十秒附近的一秒窗口发心跳，任务稍有延迟可能错过。更可靠的方式是“当前时间－上次成功发送时间 ≥ 心跳周期”。

慢拍照仍要单独处理，不要让上传长期阻塞保活。

### 9. HTTP接收队列水位造成等待

当单个 TLS 数据块本身大于缓冲水位时，如果始终要求“加入后不能超过水位”，可能连空队列都不接收，读写双方无法前进。

接收策略要允许一个大块进入空队列，或先拆块；同时限制总资源，不能改成无限堆积。

### 10. 字符串格式在桌面正常，设备上事件编号却错了

精简 printf 配置可能不支持某些64位格式。事件 ID 应在实机验证，而不是只看编译通过。可将64位随机数拆成两个明确支持的32位格式，再加递增序号。

错误编号会破坏去重，造成后续事件冲突或计数异常。

### 11. “刚才摸了几次”却读出所有历史测试次数

历史累计和本轮新增必须有独立接口或明确范围。

推荐持久游标：按读取者记录上次事件 ID，查询只聚合其后的事件。首次建立基准，不把过去所有测试算成新事件。

不同 AI 客户端使用不同游标，避免互相抢先推进。游标推进不删除历史；查询结果丢失后的恢复也要设计。不要同一次报告连续调用两个共享游标的新增接口。

### 12. 把转码上限当作播放验收

允许转码到某个时长，并不等于设备已经能稳定下载、解码和播放同样长的文件。先验收短片，再逐步增加长度，保留失败数据。

### 13. 把单次成功写成“长期稳定”

至少分别验证：短语音、带字幕表情说话、拍照、拍后仍在线、模式退出、本地互动、重启后的队列保留。一个成功样本不能替代压力与长时观察。

## 七、推荐验收清单

- [ ] 备份可读、哈希正确、回滚路径明确。
- [ ] 设备真实型号、显示驱动和分区匹配。
- [ ] MCP 公网可达、OAuth 可用、设备凭据独立。
- [ ] 小智模式正常，远程修改被设备与服务器拒绝。
- [ ] 远程页面可自行进入、退出后控制权正确恢复。
- [ ] 有界转头可观察，结束或退出后没有遗留动作。
- [ ] 表情可见、结束恢复、本地触摸反馈仍有效。
- [ ] TTS实际有声、字幕一致、播完清理，无回声误入队。
- [ ] 拍照返回真实图片，失败时能辨别抓拍与上传阶段。
- [ ] 拍照后桥接仍在线；TLS修改后其他功能不退化。
- [ ] 触摸/摇晃去重、持久化、时间与新增范围正确。
- [ ] 设备重启后，已上传留言仍保留。
- [ ] unknown不会触发自动重复拍摄、说话或动作。
- [ ] 文档明确说明自主聊天是否实现，不夸大订阅连接器能力。
